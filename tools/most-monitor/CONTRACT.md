# Most Monitor v1

Private local tool. Python stdlib; no model calls, credential copies, API spend or runtime/model switches.

`collectors.collect_codex(config)`, `collectors.collect_claude(config)` and `collectors.collect_deepseek(config)` each return one account dict, including on errors. They are bounded to 40 seconds. Config is local JSON with `dataDir`, `snapshotPath`, `identitySalt`, `enabledProviders`, `codexPath` (optional explicit pin), `claudePath` (needed only when Claude is enabled), `deepseekKeyFile` (optional path of an existing local dotenv), `deepseekKeyVar` (default `DEEPSEEK_API_KEY`), `minIntervalSeconds` (optional per-provider override), `port` (1236), `pollSeconds` (300), and `notifications` (true). `enabledProviders` accepts a nonempty unique subset of `codex`, `claude` and `deepseek`. A missing setting in existing configs defaults to `codex` and `claude` for compatibility; new installs default to `['codex']`.

DeepSeek reads `GET https://api.deepseek.com/user/balance` with the key from the process environment variable, else from that one variable of `deepseekKeyFile`. The key is never copied, logged or exported; `accountRef` is the salted hash of the key, because the API exposes no account id. HTTP 401/403 is `auth_required/login_required`, 429 `rate_limited`, anything else a fixed safe reason.

Collection cadence: a fresh account is collected again only after its provider interval (`codex` 0 s, `claude` 220 s, `deepseek` 220 s). An explicit `maxAge` below the interval allows a read after `max(60, maxAge)` s; a manual `POST /most/v1/refresh` and an expired `validUntil` (reset due) after 60 s. A manual refresh that joins a round already running gets one round of its own after it; when the joined round took over 15 s, that round runs behind the answer so a reader's ~50 s budget holds. Claude never goes under 60 s, whatever the config says. A failed account follows the separate backoff of 60 s doubling to 3600 s. A usage read triggers a refresh only when an old or missing account has a provider that may be collected now; otherwise it returns the stored snapshot, so a polling reader cannot turn a failing provider into a collection loop. On start the service seeds its cache from accounts the stored snapshot still shows fresh, so a restart does not re-read them at once. The DeepSeek request follows no redirect (the key may only reach api.deepseek.com) and uses a 10 s socket timeout per step.

Codex binary resolution happens for every collection. In order, use process `CODEX_CLI_PATH`, the narrowly parsed `mcp_servers.node_repl.env.CODEX_CLI_PATH` (or legacy top-level key) in actual `~/.codex/config.toml`, a valid explicit `codexPath`, then probe binaries under the official user-local `AppData/Local/OpenAI/Codex/bin/*/codex.exe` install and select the highest reported `--version`. Probing is bounded to two seconds per candidate and eight seconds total. Never use `PATH` or disclose/read any other TOML values. If none is available, return `error/codex_executable_unavailable` with no paths in the reason. The configured `dataDir` remains the subprocess working directory. Claude collection and its CLI path are never touched while disabled.

Disabled providers are excluded from collector scheduling and every current snapshot/export/history/alert/notification view. Their SQLite samples and alert records are retained. Pending notifications belonging to a provider disabled on service start are retired without delivery, so re-enabling later does not send an old toast.

Times are UTC Unix seconds. Numbers must be finite; null is not zero. All text is data, never HTML. No email/raw ID/token output.

Account: `{provider: 'codex'|'claude'|'deepseek', accountRef: string, label: string, authMode: 'subscription'|'api_key'|'unknown', status: 'fresh'|'stale'|'unknown'|'error'|'auth_required'|'unsupported', reason: string|null, source: string, observedAt: number|null, receivedAt: number, validUntil: number|null, coverage: string[], windows: Window[], plan: string|null}`. A DeepSeek account has `windows: []` and adds `is_available: boolean` and `balance_infos: [{currency: 'USD'|..., total_balance: string, granted_balance?: string, topped_up_balance?: string}]`. Amounts stay the provider's decimal text; an unexpected shape is `error/balance_shape_unexpected`, never a zero balance. A failed read keeps the last known balance, marked as not fresh.

Window: `{poolId: string, windowId: string, label: string, scope: object, windowKind: 'fixed'|'rolling'|'unknown', windowMinutes: number|null, metricKind: 'usage_percent', unit: 'percent', value: number|null, usedPercent: number|null, resetsAt: number|null}`. Scope preserved, model restrictions separate. Stable windowId independent of reset. Epoch reset normalized to whole minute to absorb provider timestamp jitter. No invented short window if missing/zero duration. Unknown scope is retained, never presumed equivalent to a model name. Codex coverage explicitly excludes ordinary ChatGPT chat limits.

Snapshot: `{schemaVersion:1, snapshotId:string, hostId:string, collectorVersion:'1.0.0', receivedAt:number, validUntil:number|null, status:string, accounts: Account[], alerts: Alert[], notificationStatus: string}`. Top-level `validUntil` is the earliest `validUntil` of the fresh accounts only (null when none is fresh): a failed provider keeps its old value on its own account and must not expire the snapshot for readers of another provider, such as the legacy tray reading Codex. Core adds `daily: [{poolId,windowId,scope,date,epoch,baselineAt,deltaPp,partial:true,hasGap:boolean}]` to each account. This is observed change since first comparable sample of the local day (Europe/Berlin), not reconstructed midnight use. Only weekly windows (10080 minutes), same identity/plan/reset; a decrease starts new segment, never accumulates positive steps. Persistent daily/window alerts with highest threshold only on first high sample (70/85/95), daily >=30pp. No repeats after restart. No thresholds from stale/error input. Unknown reset: persist epoch until confirmed reset/decrease; do not make one per fetch. A gap >10min sets hasGap and keeps honest measured endpoint delta.

API (127.0.0.1 only): `GET /most/v1/usage?maxAge=300` (optional `provider`, `accountRef`, `hostId` filters; host mismatch fails), `GET /most/v1/history?limit=200` and `GET /most/v1/routing-status` (recommend_model unsupported, usage_status available). Header `X-Most-Client: local-v1` required for all reads, reject any Origin and non-loopback Host; no CORS. `POST /most/v1/refresh` uses the same guard and does not mutate settings. Guarded `GET /most/v1/health` identifies the service as `most-monitor`; guarded `POST /most/v1/shutdown` acknowledges then gracefully stops its own server. The legacy bridge uses these endpoints for manual recovery, starts an absent monitor only after a refused loopback connection, and reports monitor and ChatMock outcomes separately. The monitor port defaults to 1236 and is configured by `config.port`. `MOST_MONITOR_PORT` selects the legacy bridge probe port only, so it must agree with `config.port`. API is local same-user telemetry, header protects against browser cross-origin access, not malicious local processes.

Five simultaneous usage requests with maxAge=60 share one refresh (singleflight); interval 300s with jitter, bounded backoff on failures. Accounts collected independently so one failing provider does not erase the other. Failed read preserves old observation time and last known windows, but marks error/stale and cannot appear fresh. Before a relevant window reset or after validUntil it is stale even while daemon stopped. Core materializes status on every read. Store DB outside vault, one service instance enforced by port bind before starting collectors. Atomic sanitized snapshot export after refresh.

CLI `python monitor.py usage_status --max-age 60` emits same JSON as API, works without Obsidian; default config beside monitor.py. `serve --config PATH` runs process. No CLI collection fallback when service offline, return explicit unavailable. `history` and `routing_status` support JSON. Help documents agent path. No require users to run terminal.

Windows notifications originate in daemon, not UI, persist dedup. `notifier.notify(alert)` receives allowlisted alert, returns bool. Root supplies this module. Failures shown in notificationStatus; no fake delivery claim. Keep recent alerts on panel regardless of toast success. Alert has id,kind,provider,accountRef,poolId,windowId,scope,threshold,value,createdAt,message.

Tests use fixtures/temp dirs/fake collectors/ports only. No live ECO toggles/restarts/model calls. UI shows freshness, model scopes, actual durations/resets, daily 30pp and recent alerts, plus existing Most controls. Home consumes plugin's in-memory snapshot and opens panel. Same snapshotId for all readers until new refresh. Stage4 recommendation and stage5 runner deliberately absent.
